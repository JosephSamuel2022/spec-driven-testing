Test specs you can read in a code review

A pattern for testing data-heavy planning engines: describe each scenario as a small JSON file, generate the input datasets automatically, and compare results using tolerances instead of exact matches.

The problem

Planning and optimization engines take large tables in and produce large tables out. Teams often test them with hand-built binary fixtures. Nobody can review those files in a pull request, they break when a schema changes, and writing a new one takes hours. So the tests that should catch regressions rarely get written.

The approach

SpecScenario written as JSON: inputs, rules, expected outcomes.
GenerateDatasets (such as Parquet files) are built from the spec.
RunThe engine executes against the generated data.
AssertOutputs are checked against tolerances and constraints.
ReplayValidated scenarios re-run in CI on every change.

Because a spec is plain text, a reviewer sees exactly what changed in a scenario. Because datasets are generated, a schema change means updating one generator instead of hundreds of fixtures.

What a spec looks like

{
  "scenario": "low-stock-reorder",
  "inputs": {
    "items": [{"id": "A1", "onHand": 40,
               "demandPerWeek": 90}],
    "leadTimeWeeks": 2
  },
  "expect": [
    {"field": "orderQty",
     "value": 120, "tolerance": {"abs": 2}},
    {"field": "serviceLevel",
     "value": 0.95, "tolerance": {"rel": 0.01}},
    {"field": "stockoutDays",
     "value": 0, "tolerance": {"abs": 0}}
  ]
}

Each expectation names a field, a target and how far the result may drift. Quantities may allow a small absolute margin, ratios a relative one, and counts none at all.

Constraints (such as "never order below zero") sit beside the numbers, so a run can fail on a broken rule even when every number is within range.

Why it works

Hours to minutestime to author an integration test
100+reviewable scenario specs
300+scenarios replayed to catch regressions

Tolerances keep tests stable when results shift by harmless rounding or ordering differences, while still failing on real behavior changes. Replaying validated scenarios in CI turns every past fix into a permanent guard.

Built with

Java, JSON, Parquet, Gradle CI. The pattern itself is language-agnostic and fits any engine that turns tabular data into tabular results.

This page describes a general technique with illustrative example values. It contains no proprietary code, data or screenshots.
